# Build and collect all firmware apps

From `isolde/system`, activate your usual ISOLDE tool environment, then run:

```bash
make -f Makefile.apps apps-list
make -f Makefile.apps apps-build
# Choose an export directory and FPGA build settings:
make -f Makefile.apps apps-build APP_PATH="$PWD/app-images" DBG_MODULE=1 ENABLE_SPM=1
# Or build a subset:
make -f Makefile.apps apps-build APPS="hello_test omp_test radar_attention"
```

The standalone Bash equivalent is:

```bash
APP_PATH="$PWD/app-images" ./build_apps.sh DBG_MODULE=1 ENABLE_SPM=1
```

The default collection directory is `isolde/system/app-images`. It contains
`<app>-m.ihex`, `<app>-d.ihex`, any other `<app>-*.ihex` generated by that build,
`logs/<app>.log`, and `summary.tsv`. Relative `APP_PATH` values are resolved from
`isolde/system`. Reusing the directory replaces exports for selected apps;
exports for a selected app are removed **before** building, so a failed build
cannot leave an old image looking current. Unselected apps are retained.
Logs and the summary describe the latest invocation.

The runner calls `test-clean` and `test-build` in **separate, sequential make
invocations**, then checks that both instruction and data images exist. Apps
also run serially, even if the outer make uses `-j`: their BSP directory is
shared. Do not start another firmware build concurrently. Shared source objects
are invalidated as well, so changed compiler flags do not reuse an old object.

Discovery uses immediate subdirectories of `isolde/sw` containing `.c`, `.S`,
or `.ll` files. Host tests and generator-only directories are excluded. The
legacy `onnx` directory's separate programs appear as `onnx_conv2d_test` and
`onnx_conv2d_test_lca`, each compiled with its own source. The beamformer selects
the default runtime3 backend; candidate attention, when installed, also links
its sibling beamformer runtime. Temporal `radar_attention` uses its default
encoder mode. This builds one default configuration per app, not all variants.

Generate required headers, weights and ONNX `graph.ll` files beforehand using
each app's documented preparation targets. The batch runner does not train,
regenerate inputs, run simulators, or upload to a board. Legacy apps may require
different hardware or compiler support. A build failure is recorded and the
remaining apps are attempted; the final exit status is nonzero if anything
failed. Successful compilation alone does not establish hardware compatibility.

Normal settings such as `COMPILER`, `OPT_LEVEL`, `CV_SW_TOOLCHAIN`, `BENDER`,
and `DBG_MODULE` can be passed to the outer make or as `NAME=value` arguments
to the script. The runner owns `TEST`, `TEST_SRC_DIR`, `TEST_FILES`, `PE`,
`TEST_BIN_DIR`, and `test-program` for each app; do not override those. Existing
`MAKEFLAGS` are inherited. Use `MAKE_BIN` to select a make executable if needed.
